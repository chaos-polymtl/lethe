The Lethe v1.1.0 requires the latest major release of the deal.II library (deal.ii v9.7).

As part of the v1 release, the major components of this version are detailed in the following Journal Article (which is available in open-access):
https://doi.org/10.1016/j.cpc.2025.109880

Lethe v1.2.0 introduces some key new features and bug fixes, including:
- The CHANGELOG strucutre of Lethe has been changed.
- Addition of a dimensionally consistent formulation of the Darcy force term in CLS two-phase flows simulation.
- The ``insertion acceptance function`` feature has been added.
- Addition of the new parameter `calculation frequency` to the `post-processing` subsection.
- Refactors of how the DEM boundary conditions are handled.
- The `stencil order` parameter of the sharp immersed boundary method (in the `particles/extrapolation function` subsection) has been renamed to `stencil degree`.
- Addition of the waveguide example for the time-harmonic Maxwell solver.
- Addition of the possibility to use the AMG preconditioner as the linear solver preconditioner for the Heat Transfer auxiliary physics.
- Addition of the possibility to use the AMG preconditioner as the linear solver preconditioner for the Conservative Level Set, Tracer and Cahn-Hilliard auxiliary physics.
- Addition of  the Carman-Kozeny non-linear phase change permeability model (``carman-kozeny phase change``).
- Fix of the RHS of the Darcy source term in the ``PhaseChangeDarcyCLSAssembler``.
- Fix of the ordering for the transformations of translation and rotation in box refinement.
- Fix the custom distribution sampling of the volume-based PDF with interpolation.
- Addition of the ability track ``temperature`` and ``phase`` (CLS phase indicator) isocontours in time.
- Refactor of the DEM particle-particle contact container.
- Addition of a new insertion method called the ``packed`` method.
- Addition of a new `impinging_jet_mixer` mesh lethe grid generator was added (selectable through the `type = lethe` parameter).
- Fix of a bug that prevented `lethe-fluid-particles-matrix-free` simulations from restarting consistently.
- Fix of a bug that corrupted the void fraction history stored in the checkpoint of `lethe-fluid-particles-matrix-free` simulations that use dynamic load balancing together with the void fraction time derivative, preventing them from restarting consistently.
- Addition of the multiphysic DEM capabilities of `lethe-particles` are now available within the CFD-DEM solvers, `lethe-fluid-particles` and `lethe-fluid-particles-matrix-free`.
- Fix the time-averaged velocity and the Reynolds stresses that were silently lost by the CFD-DEM solvers (`lethe-fluid-particles` and `lethe-fluid-particles-matrix-free`).
- Addition of the documentation of the parameters of the time-harmonic Maxwell solver and update the theory guide for the electromagnetic section.
- Addition or two parameters for the simulation control: end control, of type Patterns::Selection with options iteration and time, and iteration end, of type Patterns::Integer.
- Addition of the ability to use a different rotation axis than the z-axis when using the mortar method.
- Change of the `rotation axis` parameter in the Mortar subsection to a `rotation axis direction` instead.
- Fix of the velocity Verlet scheme  that never carried out its opening half step, so `lethe-particles`, `lethe-fluid-particles` and `lethe-fluid-particles-matrix-free` were effectively running a first-order symplectic Euler scheme instead of the second-order scheme they reported. 
- Addition of the `expand particle-wall contact search` option in DEM that allows the calculation of particle-wall overlaps with the boundary faces of the cell containing the particle, as well as with the boundary faces of neighboring cells.
- The time-harmonic Maxwell solver now has temperature-dependent physical properties using a polynomial model.
- Addition of probes to the postprocessing module. 
- Addition of  a new grid generator for a cube mesh, which is a combination of an extruded plate with hole and a cylinder (both generated along the z axis).
- Fix of a crash (`BDF coefficients were requested without a BDF method`) occurring when a `viscous` or `ramp` initial condition was combined with a transient or `steady_bdf` time-stepping method, as is the case in the flow around a sphere example. 
- Fix a bug for the time-harmonic Maxwell solver when performing h-adaptive refinement that was leaving unconstrained hanging-node in the interior solution in parallel.

### Added

- MAJOR Adds probes to the postprocessing module. This allows evaluation of solved variables at remote points of the domain (not necessarily a DoF). Values are outputted in ``.dat`` files (1 per probing point). Each probing point is characterized by a unique ID and a user-specified ``location``. Multiple variables can be evaluated at a same probing point and values will be written in the same output file. The first column of the file is the time and the subsequent columns are either evaluated scalar fields or components of evaluated vector fields.
  Remote point evaluation is done by the functions ``evaluate_values_at_points()`` using Utilities::MPI::RemotePointEvaluation<dim, dim>. It was added to the utilities of Lethe. It is templated for both scalar and vector evaluations.
  This implementation introduces a new PostprocessingProbes<dim> class which evaluates quantities of interest at probing points and holds all the data tables of probes. It is instantiated as a member of the MultiphysicsInterface<dim> class. Evaluation of each physics' probed quantities is done within the ``postprocess()`` (or ``postprocess_fd()``) attribute of the physics by communicating to PostprocessingProbes<dim> through the MultiphysicsInterface<dim> object. The probe tables' management (i.e., writing in output files, serializing, deserializing) is handled by the PostprocessingProbes<dim> object. Evaluations are made at the ``calculation frequecy`` specified in the ``post-processing`` subsection of the parameter file.
  At the moment, the probes are only implemented for the following variables: velocity, pressure, phase, and temperature. Other variables will follow in a future PR.
  A unit test was added to test both the scalar and vector evaluation of ``evaluate_values_at_points()``: ``evaluate_values_at_points.cc``. Two ``lethe-fluid`` application tests were updated to test the new feature (``cls-velocity-extrapolation`` and ``heat_transfer_stefan``).

  This implementation required points to describe the location of probes, as a consequence the Parameters::PostProcessing struct needed to be templated with ``dim``.  Appropriate updates due to this change were made in the code.

## [Master] - 2026/08/04

### Fixed

- MAJOR The velocity Verlet scheme never carried out its opening half step, so `lethe-particles`, `lethe-fluid-particles` and `lethe-fluid-particles-matrix-free` were effectively running a first-order symplectic Euler scheme instead of the second-order scheme they reported. The three solvers guarded the half step with `simulation_control->get_iteration_number() == 0`, but `SimulationControlTransient::integrate()` increments the iteration number before the body of the time loop runs, so the counter is always greater than or equal to one inside the loop and the branch was dead code. The scheme is now completed on both ends. The opening step advances the velocities by half a time step and the positions by a full time step, which starts the staggering without losing any physical time, and the closing step re-evaluates the forces at the final position of the particles and advances the velocities by half a time step, which synchronizes them with the positions. Completing `n` time steps therefore requires `n+1` integration operations. In pure DEM, the closing step is carried out once the time loop is over and is followed by an additional particle statistics report, announced as `Synchronized particle statistics` and subject to the usual `log frequency`, which reports the velocities at the same time as the positions. In CFD-DEM, it is carried out at the end of the DEM sub-iterations of every CFD time step, so that the drag and the post-processing of the next CFD time step see velocities that are synchronized with the positions rather than lagging by half a DEM time step. Two latent bugs in the opening step were fixed at the same time, both of which only became reachable once the step started executing: it did not reset the force and the torque containers, which the contact force objects accumulate into and which would therefore have leaked into the second time step, and it advanced only `dim` velocity and angular velocity components rather than three, which in 2D skipped `omega_z`, the only axis of rotation there is. The restart path is unaffected, since checkpoints are written inside the time loop and therefore store the staggered velocities that a restarted run resumes from. Note that particles inserted after the first time step still receive a full velocity step rather than an opening half step, which remains to be addressed. A `velocity_verlet_free_fall` application test, which monitors the velocity magnitude of a single particle in free fall through the DEM statistics, and a rewritten `integration_velocity_verlet` unit test, which checks the complete opening, regular and closing sequence in 2D and 3D against the analytical solution of a uniformly accelerated motion, were added. The parameter documentation of `integration method` and the velocity Verlet section of the DEM theory guide were updated accordingly. This changes the results of every DEM and CFD-DEM simulation that uses the velocity Verlet scheme, which is the default, and the golden output of the affected application tests was regenerated. [#2082](https://github.com/chaos-polymtl/lethe/pull/2082)

### Changed

- MAJOR The `Integrator` interface now exposes the three stages of a time integration scheme as `integrate_start`, `integrate` and `integrate_end`, instead of the previous `integrate_half_step_location` and `integrate` pair. The solvers call `integrate_start` at the first time step, `integrate` at every subsequent one and `integrate_end` once the final position is reached, without ever querying which scheme is in use: it is up to the scheme, and no longer to the caller, to decide what an opening and a closing step mean. `VelocityVerletIntegrator` implements them as the opening and the closing half velocity steps described above, whereas `ExplicitEulerIntegrator`, which is self-starting and keeps its velocities synchronized with its positions, implements `integrate_start` as a regular step and `integrate_end` as a reset of the force and the torque containers. That reset is part of the contract of every integration entry point and is not optional: the force evaluation which precedes `integrate_end` fills the containers, and the contact force objects accumulate into them, so leaving them untouched would double-count the forces of the next time step. An adaptive-sparse-contacts overload of `integrate_end` was added for symmetry with `integrate`; it advances only the particles of the mobile cells and resets the force and the torque of the others. The `torque` and `force` arguments of `integrate_start` are no longer `const`, since the opening step now resets them as well. [#2082](https://github.com/chaos-polymtl/lethe/pull/2082)
- MAJOR This PR changes the `rotation axis` parameter in the Mortar subsection to a `rotation axis direction` instead. Since the rotation axis is always going to be either x, y or z directions, it is more adequate to prescribe the rotation axis direction instead of a unit vector. This simplifies the code implementation. [#2083](https://github.com/chaos-polymtl/lethe/pull/2083)

## [Master] - 2026/07/29

### Fixed

- MINOR The time-averaged Reynolds shear stresses (`reynolds_shear_stress_uv`, and in 3D `reynolds_shear_stress_vw` and `reynolds_shear_stress_uw`) were computed by `AverageVelocities` but were no longer written to the output files, so only the normal stresses and the turbulent kinetic energy appeared in the results. The `add_data_vector` call for the shear stresses was dropped when the output was refactored into `OutputStructSolution` objects, leaving the corresponding name and component interpretation vectors unused. The shear stress output struct is now added back in `NavierStokesBase::write_output_results`. [#2074](https://github.com/chaos-polymtl/lethe/pull/2074)
- MAJOR The time-averaged velocity and the Reynolds stresses were silently lost by the CFD-DEM solvers (`lethe-fluid-particles` and `lethe-fluid-particles-matrix-free`) in two situations. First, `CFDDEMSolver::load_balance` and `CFDDEMMatrixFree::load_balance` transferred the fluid solutions, the void fraction and the particle handler to the new partition, but not the averaging accumulators. The `setup_dofs` call that follows the repartitioning reinitializes those vectors, so the accumulated sums were reset at every load balance while `real_initial_time` was left untouched. The averaging numerator therefore only covered the time elapsed since the last load balance whereas the denominator still spanned the whole averaging window, and the average velocity and Reynolds stresses decayed towards zero as the simulation progressed. The two `load_balance` implementations now transfer the averaging vectors with `AverageVelocities::prepare_for_mesh_adaptation` and `AverageVelocities::post_mesh_adaptation`, as the mesh adaptation of the other fluid solvers already did. Second, `CFDDEMSolver::read_checkpoint` and `CFDDEMMatrixFree::read_checkpoint` duplicate the restart logic of `NavierStokesBase` and were never updated when `AverageVelocities::read` started deserializing into the vectors with ghost cells. The locally owned sum vectors, into which the averaging routines accumulate, were consequently left at zero after a restart, with the same effect on the averages, and the corrupted state was propagated to every subsequent checkpoint. The shared logic is now factored into `NavierStokesBase::restore_average_velocities_after_checkpoint`, which is called by the three `read_checkpoint` implementations. This also gives the CFD-DEM solvers the reinitialization of the average when the initial averaging time has not been reached yet, which was previously only available in the other fluid solvers. The condition deciding whether the average velocity vectors must be preserved is now expressed by `NavierStokesBase::average_velocities_are_enabled` so that it stays identical everywhere those vectors are serialized, deserialized or transferred. Finally, restarting a simulation used to accumulate one spurious contribution into the Reynolds stresses. `NavierStokesBase::read_checkpoint` called `calculate_average_velocities` once after the deserialization to give the averaged fields a meaningful value, but at that point `local_evaluation_point` had been zeroed by `setup_dofs` and is not restored from the checkpoint, so a fluctuation equal to the full average velocity was added to the Reynolds stress sums at every restart. The averaged fields are now reevaluated from the checkpointed sums instead: `AverageVelocities::sanitize_after_restart` takes the restart time as an argument, restores the total averaging time from the checkpointed start time of the averaging, and calls `AverageVelocities::update_average_velocities`. The averaged fields of a restarted simulation are consequently identical to those of an uninterrupted one, which is verified by the new `average_velocities_04` and `average_velocities_05` unit tests. Those two tests carry out the same time steps, the first one interrupting them with a mesh refinement and the second one with a restart, and are expected to print the same values. [#2074](https://github.com/chaos-polymtl/lethe/pull/2074)

## [Master] - 2026/07/28

### Added

- MAJOR The multiphysic DEM capabilities of `lethe-particles` are now available within the CFD-DEM solvers, `lethe-fluid-particles` and `lethe-fluid-particles-matrix-free`. Setting `set solver type = dem_mp` in the `model parameters` subsection makes the particles carry a temperature and a specific heat, enables the conductive heat transfer between the particles, and integrates their temperature within the DEM sub-iterations. A new `DEM::CFDDEMMPProperties` index set was added for this purpose; it appends the thermal properties after the CFD-DEM ones so that it shares the exact layout of `DEM::CFDDEMProperties` for every property they have in common, an invariant which is enforced by a `static_assert`. The `PropertiesIndex` template parameter, which the DEM components already used, was propagated to `CFDDEMSolver`, `CFDDEMMatrixFree`, `FluidDynamicsVANS`, `FluidDynamicsVANSMatrixFree`, `ParticleProjector` and the particle-fluid VANS assemblers, and the applications now dispatch on the solver type. The particle-touching member functions of `NavierStokesScratchData` and `MFNavierStokesVANSPreconditionGMG::initialize` became member templates rather than class templates, so that the classes shared with the other Navier-Stokes solvers remain templated by the dimension only. Since the solver type only indicates that the DEM has its multiphysic features enabled, the `model parameters` subsection of a DEM packing simulation can be reused as-is in the CFD-DEM simulation which follows it, and `convert_particle_handler` now carries the temperature and the specific heat of the particles over when a multiphysic CFD-DEM simulation is restarted from a multiphysic DEM one. Note that the fluid and the particles do not exchange heat with one another, and that the particle-solid object heat transfer is not available since the CFD-DEM solvers do not support solid objects. The `3d-heat-transfer-in-aligned-particles` example was ported to `lethe-fluid-particles` in the new `unresolved-cfd-dem-multiphysics` example folder. ## [Master] - 2026/07/24

### Fixed

- MINOR The `waveguide` multiphysics example now explicitly sets `set preconditioner = none` in its `electromagnetics` linear solver subsection. - MAJOR Fixed a bug that corrupted the void fraction history stored in the checkpoint of `lethe-fluid-particles-matrix-free` simulations that use dynamic load balancing together with the void fraction time derivative, preventing them from restarting consistently. In `load_balance`, the fluid solution vectors have their ghost values refreshed after the `SolutionTransfer` interpolation onto the repartitioned mesh, but the void fraction vectors (`void_fraction_solution` and `void_fraction_previous_solution`) did not. `interpolate` only fills locally owned entries, so the void fraction vectors were left with stale ghost values. When a checkpoint was written on a load balance step, these stale ghosts were first propagated by `percolate_void_fraction` (which copies whole vectors) and then packed into the checkpoint by `prepare_for_serialization`, which reads ghost values to serialize the dofs of locally owned cells that sit on a subdomain boundary. The checkpoint therefore stored incorrect void fractions on those dofs, most notably in the second previous solution used by BDF2. On restart, the void fraction time derivative multiplies this error by a factor scaling as 1/dt, injecting a large spurious source in the continuity equation that led to an abnormally high first Newton residual and a loss of convergence. The ghost values of the interpolated void fraction vectors are now refreshed in `load_balance`, and, defensively, the deserialized void fraction vectors are re-ghosted in `read_checkpoint` to keep the invariant that these vectors are always ghosted outside of a solve. Note that checkpoints written by an affected run already contain the incorrect boundary values and must be regenerated. [#2069](https://github.com/chaos-polymtl/lethe/pull/2069)

## [Master] - 2026/07/08

### Added

- MAJOR A new `impinging_jet_mixer` mesh lethe grid generator was added (selectable through the `type = lethe` parameter). It builds a fully hexahedral, conforming mesh for an impinging-jet mixer: a vertical cylindrical mixing chamber closed at the top by a hemispherical dome, a conical reduction followed by a straight outlet pipe below the chamber, and two opposing horizontal inlet pipes entering the chamber side wall from `+x` and `-x`. Because a round pipe meeting the curved chamber wall is a saddle intersection that cannot be produced by merging library primitives, each inlet pipe is instead grown out of the refined chamber wall itself, so the junction stays watertight and conforming. The two inlets share a common axis and the mesh is datumed so that axis lies on the `z = 0` (impingement) plane. The `grid arguments` accepts either an empty string (default dimensions) or exactly eight colon-separated dimensions in meters, in the order `R_chamber : r_inlet : r_outlet : H_chamber : L_cone : L_outlet : L_inlet : z_inlet`; the discretisation is fixed internally and not exposed. Boundary IDs are 0 for the `+x` inlet, 1 for the `-x` inlet, 2 for the outlet, and 3 for all walls. This mesh will be featured in a future example. [#2059](https://github.com/chaos-polymtl/lethe/pull/2059)
- MAJOR This PR adds a new insertion method called the ``packed`` method. This insertion method inserts particles in an insertion box in an unstructured manner without guaranteeing that the particles are not overlapping on insertion. Overlapping particles are then shifted apart, relative to their normal contact vector, until all particles are no longer touching each other or walls. This particle shifting is performed using pseudo time-stepping, where gravity is not considered and where the equations of motion on every particle are not solved. This method should be useful when dealing with a large number of particles in a tight triangulation, which forces the use of multiple insertion boxes when using the ``volume`` insertion method. [#2033](https://github.com/chaos-polymtl/lethe/pull/2033)

However, the `TrilinosWrappers::SparsityPattern` do not have the `memory_consumption` function and it is therefore not clear if the cost is really reduced as the proxy used to estimate it (`sparsity_pattern.n_nonzero_elements() * sizeof(TrilinosWrappers::types::int_type) * bytes_to_gb;`) actually show an increase in memory usage in comparison to the value obtained from `dsp.memory_consumption()`. Finally, the sparsity pattern and the sparse matrix are now only set up when the function `should_solve_auxiliary_physics()` returns true. Again this is to free memory when the THM solver is not required to be called. [#1998](https://github.com/chaos-polymtl/lethe/pull/1998)

### Added

- MINOR A new feature to the `grid_uniform_channel_with_meshed_cylinder` and `grid_uniform_channel_with_meshed_square_prism` is added so it is now possible to mesh or not the obstacle inside the channel. The default behavior of the meshes is also change so the obstacle is not meshed.[#1997](https://github.com/chaos-polymtl/lethe/pull/1997)

### Added

- MAJOR This PR enables the LSMG (local-smoothing multigrid) preconditioner for the VANS matrix-free solver (`lethe-fluid-vans-matrix-free`). When `set preconditioner = lsmg` is selected for fluid dynamics, the auxiliary particle-projected fields (void fraction, particle-fluid force, drag, particle velocity, momentum transfer coefficient) now have multigrid level DoFs distributed via the `ParticleProjector`, and one `MGTransferMatrixFree` per field is built to interpolate the fine vectors to every triangulation level. The VANS operator is extended to handle level cell iterators on coarse multigrid levels (gathering values via the mg dof indices instead of the active-cell `get_function_values` path). Only pure h-coarsening is supported on the LSMG path; mortar coupling and the FE_Q_iso_Q1 coarse-grid option are blocked with explicit assertions. Simplex meshes are now also explicitly rejected by the VANS matrix-free solver at construction to ensure that the code is a bit more defensive. [#1991](https://github.com/chaos-polymtl/lethe/pull/1991)

### Fixed

- MINOR The GCMG (global-coarsening multigrid) preconditioner of the VANS matrix-free solver was building the particle-fluid force transfer twice and never building the particle-fluid drag transfer (copy-paste bug). This left the drag contribution missing on coarse multigrid levels. The correct transfer is now built for each auxiliary field. [#1991](https://github.com/chaos-polymtl/lethe/pull/1991)
